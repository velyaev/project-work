# Design-Doc: Чат-бот / RAG-система

/ основан на шаблоне команды [Reliable ML](https://github.com/IrinaGoloshchapova/ml_system_design_doc_ru/blob/main/ML_System_Design_Doc_Template.md) /

(Заполняется проектной командой: бизнес-заказчик, ML/инженеры, продуктовая команда)

## 1. Контекст проекта

### 1.1 Бизнес-задача

•    **Описание проблемы:** каждый год абитуриенты задают повторяющиеся вопросы о поступлении. Поиск ответов на официальных сайтах занимает много времени, а приёмная комиссия вынуждена отвечать на однотипные запросы вручную.

•    **Почему именно чат-бот?** Потому что обычно все приёмные комиссии ведут диалог с абитуриентами именно в Telegram, поэтому чат-бот будет удобен всем.

•    **Каковы критерии успеха с точки зрения бизнеса.**
Будем считать, что если мы сможем немного разгрузить учебный офис и кураторов от ответов на простые вопросы, то проект можно считать успешным.




### 1.2 Целевая аудитория и пользователи
• **Кто будет пользоваться ботом:** абитуриенты, родители абитуриентов

• **Какие сценарии использования**: текстовый чат.

• **Какова предполагаемая нагрузка:**
Если делать бота для всего факультета, например, для ФКН, то число пользователей может быть больше 5000.
Пиковые даты — начало приёмной кампании (примерно май) и период до конца приёмной кампании (конец августа).


### 1.3 Ограничения и допущения


Бот не только не должен отвечать на вопросы, которые не связаны с поступлением, но и не придумывать свои ответы, если не нашел точного ответа в офицальных данных.
Ответы на вопросы должны быть получены только из официальных источников.


## 2. Архитектура решения (пока что в процессе)

### 2.1 Общая схема
1) Обработка данных

Пулл страниц и пдф ( я решил, что будет сначала только фиксированный пулл страниц, которые будем использовать)  -> Парсер ( будем скачивать сайт/пдф и извлекать только нужный текст)  -> приведение к единому формату ( нужно будет удалять ненужные элементы на сайте, такие как меню, навигацию и еще разные кнопки) -> разделяем на блоки -> embeddings -> сохраняем  все embeddings в ВБ ( думаю, можно в ChromaDB) ->
RAG-движок -> Чат-бот

### 2.2 Хранилище знаний / документооборот
***Источники знаний:*** Пулл страниц и пдф

***Предобработка:*** парсинг

***Индексация:*** векторизация (embedding)

***Обновление данных:*** думаю, можно раз в неделю, если будет ручное обновление


### 2.3 Retrieval + Generation ( в процессе)
    •    Retrieval: какой движок (Qdrant, FAISS, Elastic Vectorembedding и т.д.), конфигурации (embedding модель, размер векторов, k, threshold).
    •    Generation: какая LLM используется (локально / облако), с какими промпт-шаблонами.
    •    Контроль ответа: фильтрация, шаблоны, гарантия качества, fallback стратегия.
-- технические решения, можно к КТ1 не писать, но просто прикинуть, что будет актуально; но аргументировать выбор перед защитой на основе бизнес-требований.

### 2.4 Интеграции и интерфейсы ( в процессе )
    •    Внешние API и сервисы: чат-интерфейс, CRM, база пользователей, логирование.
    •    Протоколы: REST, gRPC, WebSockets, Webhook.
    •    UI/UX: как выглядит чат, переходы, кнопки, предложения.
    •    Мониторинг: логирование запросов/ответов, аналитика, алерты.

### 2.5 Инфраструктура и развертывание ( в процессе)
    •    Архитектурный стек: контейнеры (Docker), оркестрация (Kubernetes), серверless.
    •    Среды: dev/test/prod.
    •    Требования к вычислениям: GPU или CPU, память, хранилище.
    •    Безопасность: аутентификация, авторизация, шифрование, GDPR/нормы.
    •    Масштабирование: горизонтальное, резервирование, локализация.

## 3. Данные и качество знаний

***Пометка:*** содежат ли документы чувствительные данные (можно ли это отправлять "во вне", например, в GPT, или можно только локальные модели; может быть придётся замаскировать данные?)

***Замечание:***
Данные можно будет отправлять "во вне", потому что они не содержат персональных данных и секретной информации.

### 3.1 Сбор и предобработка данных

https://ba.hse.ru/bolimp с этого сайта берем пдф про олипиады для ФКН

•    ***Шаги предобработки:***
Сайт: извлечение основного текста без меню, кнопок и навигации.
PDF: извлечение текста с сохранением структуры абзацев.( нам придеться делить текст на блоки и лучше, чтобы эти блоки были не просто, например, одиннакового размера, а бы ли разделены по смыслу.

•    ***Метаданные:*** будем хранить такие данные
1) Категория, чтобы быстрей искать информацию
2) Дата последнего обновления. Мы должны давать актуальные данные, поэтому нам придется их обновлять
3) Hash. Чтобы понять изменился ли текст или нет будет сравнивать Hash.

### 3.2 Векторизация и индексирование (в процессе) 
    •    Модель embedding: название, версия, особенности (например multiling, domain-specific).
    •    Параметры индекса: размер, алгоритм, метрики (cosine, euclid), shards/replicas.
    •    Стратегии обновления: инкрементальное обновление, пересборка индекса.

### 3.3 Метрики качества знаний
•    ***Покрытие:*** % документов в базе относящихся к сценариям.
•    ***Актуальность:*** обновлем данные каждую неделю
•    ***Консистентность:*** нет дубликатов ( к примеру, нет двух разных цен на одну и ту же программу), нет противоречивых данных .
•    ***Проверка:*** ручная ревизия

## 4. Модель и генерация ( пока что в процессе)

### 4.1 Выбор LLM и промптинг
    •    Указание модели: объяснение, почему выбранa.
    •    Промпт-шаблоны: входные данные, контекст, инструкции, формат ответа.
    •    Ограничения: максимальная длина, токены, скорость генерации.

### 4.2 Контроль качества ответов
    •    Метрики: точность, полнота/coverage, полезность, удовлетворённость пользователя.
    •    Оценка ошибок: нежелательные ответы, hallucinations, офтопик.
    •    Механизмы: ручной ревью, эвристики (например “если confidence < x, дефолтный ответ”), fallback на статический контент.

### 4.3 Обучение/дообучение

## 5. UX / пользовательский опыт

Важно: пункт 5.1 -- он определяет частично БФТ. Что делать, если не смогли ответить? Продумать, где мы можем накосячить и как это обработать?

### 5.1 Сценарии взаимодействия
*Приветствие*: Привет! Я - умный ассистент для абитуриентов ФКН. Могу ответить на вопросы, свзянные с поступлением. Задавай свой вопрос.

*Если модель не может выдать точный ответ отвечаем таким сообщением:*
"Извините, я не могу ответить на этот вопрос"



### 5.2 Диалоговая логика

Будет только одно состояние, которые не будет требовать контекста ( то есть не храним историю общения с пользователем): single-turn.

### 5.3 Метрики UX
Отвечать нужно быстро. После того как бот выдал ответ пользователя будет предложено оценить ответ на его вопрос ( думаю, просто сделать лайк или дизлайк). Будем логгировать, чтобы понять на какой вопрос был лайк, а на какой дизлайк. 



## 6. Безопасность, соответствие и этика
•    ***Обработка персональных данных, разрешения пользователей.***
Мы не будем собирать и хранить персональные данные пользователей ( можно сказать, что у нас будет анонимно)

•    ***Устранение вредоносного/нежелательного контента, фильтры.***
Бот должен отвечать так "Извините, я не могу ответить на этот вопрос", если не сможет точно ответить на вопрос ( то есть не нашел на него  ответ).

•    ***Прозрачность:***  В самом начале бот сообщит, что он - виртуальный помощник абитуриента ФКН ВШЭ.

•    ***Регулирования и нормативы (GDPR, внутренние политики).***
Проект соблюдает принципы GDPR и внутренние политики университета, а именно персональные данные не хранятся, данные, основаны на официальных документы и сайтах ВШЭ.
